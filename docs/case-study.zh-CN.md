# 案例研究：不用 unidbg，硬刚一个把 SHA-256 藏进自定义 VM 的保护

[English](case-study.md) | [中文](case-study.zh-CN.md)

> **脱敏说明。** 本文刻意匿名：不出现厂商名、包名、真实偏移、密钥或样本值。目标是某大型电商 App 的 native 签名库（单个 ARM64 `.so`）。文中所有地址与常量均为示意，仅用于讲清方法。

## 摘要

一个 native 签名库里，真正的哈希变换不是普通函数，而是一段**自解密字节码**，跑在一个 **85 条指令的自定义栈机**里。更阴的是：SHA-256 的初始化向量被拆成"两个立即数异或"，后处理常量塞进字节码尾部——所以 `strings` 搜不到魔数，黑盒比对也匹配不上标准 SHA-256。

面对同一个目标，有两条路：

- **路线 A（常见）**：用 unidbg 补环境模拟执行 `.so`，hook 拿中间值，黑盒猜算法。快，但它**绕过**了 VM——你拿到的是输入输出，永远看不到中间那层混淆。
- **路线 B（本文）**：**硬刚**——读解释器、恢复指令集、把字节码反汇编出来，逐条还原它到底算了什么。

本文讲路线 B，以及为什么有些结论只有硬刚才能得到。工具层面的沉淀就是 `vmrecover`。

## 一、它把哈希藏哪了

签名链路里有一个 16B → 32B 的变换（记为 `X25`）。在 IDA 里对它按 F5，反编译结果只有一行：

```c
void sub_XXXX()
{
  JUMPOUT(0xXXXXLL);
}
```

`JUMPOUT` 说明函数入口是 OLLVM 的跳转 thunk，真正的函数体被藏到了别处。dump 出真身汇编后，结构一眼可辨——标准的哈希三段式：

```asm
BL  sub_XXXX   ; init
BL  sub_XXXX   ; update(input, 16)
BL  sub_XXXX   ; finalize -> 32 bytes out
```

但三个函数里**看不到任何 SHA/MD5 的轮运算**，只有 `memcpy` 和函数调用。真正的算法去哪儿了？答案在 `init` 内部这几行：

```asm
ADRL X1, unk_XXXX          ; 源表（磁盘上是加密的）
MOV  W2, #2                ; 解密 key = 2
MOV  W3, #0x1AF            ; 长度 = 431 字节
BL   decrypt_str           ; 就地解密
...
BL   sub_XXXX              ; 加载字节码
BL   sub_XXXX              ; 解释器执行！
```

`解密 + 加载 + 解释执行` 三件套一出现，性质就定了：**这是一台带自解密字节码的 VM**。`unk_XXXX` 是它吃的字节码，`sub_XXXX` 是解释器。

## 二、为什么选硬刚，而不是 unidbg

unidbg 的正确打开方式，是补环境、模拟执行、hook 出中间值，然后把拿到的值拼成一个离线复现脚本。它非常高效——但要理解它**拿不到什么**：

1. unidbg 看到的是 VM 的**输入输出**，看不到 VM 的**指令**。你只知道"输入 X 得到输出 Y"，不知道中间经历了哪些运算。
2. 一旦 VM 的输出和任何标准算法**对不上**（本例正是如此，因为有一层后处理），黑盒路线就卡住了——你只能继续加 hook、加猜测。
3. 最关键的：被混淆的常量（比如拆成两半异或的 SHA-256 IV）**只存在于指令的立即数里**，运行期的内存里根本没有完整形态。unidbg 一辈子都看不到 `0x6a09e667`，因为它只出现在 `push A; push B; xor` 的**计算结果**里。

所以硬刚不是"为了炫技"，而是**这一层的结论只能靠硬刚得到**。这也是本文的核心论点：黑盒能告诉你"对不上"，只有白盒能告诉你"为什么对不上"。

## 三、硬刚四步

### 第 1 步：确认它是 VM

导出解释器整段汇编，第一眼就是决定性证据——教科书级的字节码解释器主循环：

```asm
LDRB W8, [X20]          ; 取指：从 IP 读一个字节
CMP  W8, #0x54          ; switch 85 cases
B.HI default            ; > 0x54 走 default
LDRH W10, [X26,X8,LSL#1] ; 查跳转表
BR   X9                 ; 分发
```

一个 `LDRB` 取指 + 85 项跳转表 + `BR` 分发。`X20` 是指令指针，`X21` 是栈指针，`X23` 是数据基址，`X22` 是第二寄存器——这是台栈机。

### 第 2 步：解析字节码表

三张字节码表（init/update/finalize），每张都有固定表头。表头是 **6 个 32 位字段**：

```
偏移 0x00: magic    （魔数，用于识别这张表）
偏移 0x04: lenA     主数据段长度
偏移 0x08: lenB     附加数据段长度
偏移 0x0C: dataoff  （重定位占位基数）
偏移 0x10: nreloc   重定位条目数
偏移 0x14: 保留字段（恒为 0，用途未知）
偏移 0x18: 重定位表（每条 8 字节，指向数据段内偏移）
之后:       字节码段（lenA + lenB 字节）
```

一个容易踩的坑：表头不是 5 个字段而是 **6 个**——`0x14` 处还有一个恒为 0 的字。少算 4 字节，后面整个重定位表全错位。`vmrecover.vmstruct.parse_table` 就干这件事。

init 表在磁盘上是加密态，`decrypt_str` 是位置相关的流式异或：

```python
def decrypt_str(src, key):
    return bytes((b ^ ((key + 3 * i) & 0xff)) for i, b in enumerate(src))
```

key=2，步进 3。强度不重要，目的是**防静态扫描**——让 `strings` 和常量搜索抓不到明文字节码。

### 第 3 步：写反汇编器，还原语义

把解释器 85 个 case 的语义逐一读出来，映射成指令（`push_i32`、`ld_i8`、`xor32`、`brz`、`syscall`、`halt`…）。这是纯体力活，但每一格的语义都必须从汇编里坐实，不能猜。`vmrecover.disasm.Disassembler` 把这份表接住，输出结构化指令。

### 第 4 步：从字节码里"挖"回被藏的算法

反汇编完成后，真正的发现才开始。有三样东西是黑盒永远看不到、只能从字节码里读出来的：

**① 被"双立即数 XOR"藏起来的 SHA-256 IV。**

init 表的字节码开头，反复出现这个模式：

```asm
push_i32 0x95f78fd1
push_i32 0xfffe69b6
xor32
```

把 xor 算出来：

```
0x95f78fd1 ^ 0xfffe69b6 = 0x6a09e667
0x4499c730 ^ 0xfffe69b5 = 0xbb67ae85
...
```

`6a09e667 bb67ae85 3c6ef372 ...`——这是 SHA-256 的 8 个标准 IV，一个不差。VM 把魔数拆成"加密值 + 递减密钥"两个立即数，让常量扫描永远搜不到裸的 `6a09e667`。`vmrecover.xorconst.fold_constants` 就是自动做这个折叠。

**② 重定位表把立即数换成函数指针。**

update/finalize 表里有几处 `push_i64` 的立即数是占位值（`0x240`/`0x6c0`），加载时才被替换成宿主函数的真实地址。VM 自己不算哈希，它通过 `syscall` 调宿主的压缩函数。

**③ 后处理常量塞在 finalize 表末尾。**

finalize 表末尾逐字节 push 两张 32 字节常量表，然后一个循环：

```
out[i] = (sha256[i] + t1[i]) ^ t2[i]   (mod 256)
```

这就是为什么 `SHA256(m1)` 黑盒比对一直匹配不上——VM 在标准 SHA-256 输出上额外套了一层"加 t1 再异或 t2"。常量表就埋在字节码里，只有反汇编才看得到。

## 四、验证与结论

还原出 `X25 = POST(SHA256(m1))` 之后，用受控差分测试做黑盒验证：喂多组 16 字节输入，比对我们离线算出的 32 字节输出，**8/8 命中**。

结论：这台 VM 的职责不是"自己实现哈希"，而是**编排 + 混淆**——通过 syscall 调宿主 SHA-256，再用"双立即数异或藏 IV、重定位表藏函数、后处理藏常量"三重手段，让黑盒和静态扫描同时失明。

## 五、诚实边界

- `vmrecover` **不自动恢复指令集**。opcode 语义是二进制特定的，必须由人从解释器汇编里读出来；本工具提供的是"读完之后的语义化处理层"。
- 本工具**不模拟执行**。它不跑字节码，只反汇编 + 语义识别。动态验证（Frida 差分测试、unidbg 对照）仍然是确认结论的必要一步。
- 文中所有偏移、魔数、常量均为示意，真实值需在授权样本上重新获取。

## 六、可复用成果

| 模块 | 解决的问题 |
|------|-----------|
| `vmrecover.disasm` | 给定 opcode 表，把字节码反汇编成结构化指令（含重定位标注、跳转目标） |
| `vmrecover.xorconst` | 识别 `push A; push B; op` 模式，折叠出被"双立即数运算"隐藏的常量 |
| `vmrecover.vmstruct` | 解析 VM 字节码表头（含那个容易漏算的第 6 字段）与重定位表 |

> **留一句给同行：** 模拟执行能让你"跑起来"，但被藏进指令立即数里的东西，只有反汇编才看得到。两者不是对立，是先后——先用白盒定位"为什么对不上"，再用黑盒验证"猜得对不对"。
